## Architecture and public boundary

The package is a compound React row API. Each `Root` owns gesture state,
measurements, direction normalization, focus behavior, and direct DOM motion.
`Content` is the translated foreground; measured `Leading` and `Trailing`
containers sit behind it; native-button `Action` components register their
width and optional full-swipe eligibility. `Group` coordinates only the
previously open root through an imperative registry. Application data,
side-effects, removal, undo, confirmation, async state, and virtualization stay
with the consumer.

The verified public API has 16 exports and no approved public-API deviations
from the design:

- Runtime: `Action`, `Content`, `Group`, `Leading`, `Root`, `SwipeActions`, and
  `Trailing`.
- Types: `SwipeActionsActionProps`, `SwipeActionsContentProps`,
  `SwipeActionsDirection`, `SwipeActionsGroupProps`, `SwipeActionsHandle`,
  `SwipeActionsOpenSide`, `SwipeActionsRootProps`, `SwipeActionsSide`, and
  `SwipeActionsSideProps`.
- Package subpaths: `.`, `./core.css`, `./theme.css`, `./styles.css`, and
  `./package.json` only.

The distribution supplies ESM, CommonJS, and NodeNext-compatible declarations.
React, React DOM, and the JSX runtime remain external.

## Gesture, intent, and motion model

- A primary main-button pointer begins pending. Intent stays pending inside a
  6 px radial dead zone; horizontal movement must exceed vertical movement by
  1.2× or vertical scrolling wins.
- Position samples use a 100 ms window. Release velocity is clamped to ±2 px/ms
  and projected 120 ms forward.
- The default open threshold is 0.35 of the measured side width. The default
  full-swipe threshold is 0.7 of content width, with at least 0.15 of content
  width of real travel before velocity may arm activation.
- Without a full-swipe claimant, travel resists beyond the measured side width.
  With one claimant, direct travel may continue to content width. Exactly one
  registered enabled claimant is invoked at committed release.
- Drag writes are coalesced to one `requestAnimationFrame`. Settling uses an
  internal cubic ease-out animator whose distance/velocity duration is clamped
  to 120–360 ms, with 0.75 px/ms minimum and 2.5 px/ms maximum settle speeds.
- New grabs interrupt settling from the visible coordinate. Generation guards
  prevent stale completions. Pointer cancel, lost capture, window blur, a
  second pointer, resize/configuration changes, direction changes, side
  removal, and unmount cancel transient work and reconcile to authoritative
  state.
- Reduced motion writes the destination immediately and schedules no settle
  frame. Completed trusted touch/pen drags use target- and pointer-scoped click
  suppression for at most 400 ms.

## Accessibility, keyboard, direction, and styling

The focusable root uses physical `ArrowLeft`/`ArrowRight` edges, then converts
them to logical sides. Thus RTL ArrowRight opens logical `leading` and RTL
ArrowLeft opens logical `trailing`. Keyboard opening focuses the first enabled
revealed action; `Escape` closes and restores root focus when needed. Inactive
sides use `inert`, `aria-hidden`, and managed descendant `tabindex` fallback.
Actions are native `button type="button"` elements. Disabled roots leave normal
content interaction available.

Public state always uses `leading`, `trailing`, or `null`. An explicit
`direction` wins over computed ancestry. Runtime direction mutation cancels
transient movement and remaps the same logical resting side. Imports are
SSR-safe and browser resources begin after mount.

`core.css` is the required mechanical contract: layering, clipping, logical
edge placement, transforms, reveal availability, full-swipe expansion, and
`touch-action: pan-y`. `theme.css` is optional neutral presentation and must
follow core. `styles.css` combines them. Documented data attributes and CSS
variables are stable hooks; package class names are not.

## Confirmed audit defects and regression evidence

1. `npm run check` failed with four `no-undef` errors for `process` in
   `scripts/verify-workflows.test.mjs`. Root cause: the Node test added in
   `64a58f9` was absent from the flat-config `.mjs` globals rule. The failing
   clean lint gate was the RED regression. Adding that file to the existing
   Node/browser globals rule made focused ESLint and the full check pass.
2. The interaction guide reversed the verified RTL arrow mapping. The new
   nearest package regression failed against the incorrect `ArrowLeft` →
   `leading` wording, then passed after the guide was corrected to
   `ArrowLeft` → `trailing` and `ArrowRight` → `leading`. The assertion permits
   Markdown whitespace so it checks semantics rather than line wrapping.

No runtime interaction defect was reproduced by the complete matrix or focused
repeats.

## Known limitations and manual checks

- No physical Mobile Safari or Chrome Android device was available. Browser
  back-edge navigation ownership was not tested and is not inferred from
  desktop automation.
- No real third-party Bottom Sheet integration was run. Automated
  dialog/sheet-like containment passed, but it does not establish compatibility
  with a particular sheet version, handle, snap-point, or gesture configuration.
- Native continuous-touch vertical competition was automated only in Chromium;
  Firefox/WebKit used synthetic touch fallback for swipe coverage and skipped
  this trusted-touch case.
- Actual Microsoft Edge, Chrome Android, Mobile Safari, assistive technology,
  and physical-device performance were not run in this local audit.
- Nested swipe roots, portals, `asChild`, React Native, drag-and-drop ownership,
  automatic removal, undo, confirmation, async mutation state, and built-in
  virtualization are unsupported or intentionally application-owned.
- Fully mounted list cost grows with rows and observed elements. Consumers own
  virtualization and must validate transformed layouts and custom scrollers.

The support policy targets current and previous major Chrome/Chromium, Edge,
Firefox, and Safari releases plus modern Chrome Android and Mobile Safari. The
three exact desktop engine builds above are the automated evidence for this
candidate; the broader policy is not a claim that every named browser/device was
executed locally.

These limitations and the need for real-world gesture/API validation are why
the recommended classification remains `0.1.0-alpha.0`.
